# Customer Database

> A topic profile maintained by API Evangelist covering APIs, schemas, vocabularies, and
> reference designs for the systems of record that hold customer identity, profile,
> contact, preference, consent, and account data. This is a REFERENCE topic, not a
> company: it documents no vendor API of its own and has no base URL, no authentication,
> and no endpoints. For a vendor's actual API, follow the vendor links below to that
> vendor's own profile.

## What this profile is

A customer database underpins CRM, marketing automation, customer data platforms,
customer service, billing, and analytics. It is increasingly expected to support
API-first access, schema-on-write data quality, real-time eventing, GDPR/CCPA consent and
erasure workflows, and identity resolution across web, mobile, and offline channels.

This repository holds neutral, standards-grounded artifacts you can map a vendor or an
in-house customer store against.

## The three standards this model is built on

- [SCIM 2.0 Core Schema — RFC 7643](https://www.rfc-editor.org/rfc/rfc7643.txt): the
  core User schema and the enterprise extension.
- [SCIM 2.0 Protocol — RFC 7644](https://www.rfc-editor.org/rfc/rfc7644.txt): REST
  provisioning, PATCH semantics, bulk operations, filtering.
- [vCard 4.0 — RFC 6350](https://www.rfc-editor.org/rfc/rfc6350.txt): the contact
  interchange format.
- [Schema.org Person](https://schema.org/Person): profile description for the open web.

## What none of them cover

Two things a real customer database cannot work without have no open standard at all:

1. **Consent.** SCIM provisions accounts, vCard interchanges contacts, Schema.org
   describes people. None models purpose, legal basis, or withdrawal history. Every
   vendor therefore invents its own consent model, which is why consent data is the
   hardest thing to port between platforms.
2. **Identity resolution.** There is no standard way to say "these two records are the
   same person, matched probabilistically at 0.87 confidence", so identity graphs are
   entirely proprietary and non-portable.

Both gaps are modeled explicitly in this repository so at least the shape of the problem
is written down.
